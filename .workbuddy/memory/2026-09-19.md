### ★ 核心教训：**「伤害代理」不是伤害**

代理是**线性加权和**，对本流派（攻速 × 流血/穿刺平伤）权重明显偏低 → 会选错。
实测：代理 951 的解真实 26k；代理 988 的解真实 26.6k；**现状代理 836 却真实 38.5k**。
→ 「拉高伤害」必须用 `tools/plan_dps.py`（真实 `final_report` 模型）当目标函数。

### ★ 另一个坑：`--goal maxdmg` + `GD_COVER_MIN` 到不了满抗

总覆盖 = Σ min(抗性, 需求)，跨槽会重叠截断 → 是**乐观上界**（设 COVER_MIN=1070 只能到 998）；
且它的逐槽 `sufcap` 剪枝**不含稀有度预算**，乐观放行后收不了尾。
要满抗用 **`GD_FULL=1` + `--goal worst`**（逐维硬剪枝，实测 1070/1070）。
但 GD_FULL 会让小束宽找不到解 → 启动/`--compare` 时必须关掉 GD_FULL。

|---|---|
| ★★ `rotation.py:807 skill_children()` 每次评估重算 12 372 条技能库父子表（3 339 次正则 + 3 339 次路径处理），占 final_report **89 %** | 记忆化 → 单次评估 **0.0255→0.0078 s（3.3×）** |

受 Amdahl 限制。**更优解：并行多条独立搜索链取最优**（无共享状态，近线性）。

**★ 必须先修的 bug**：不同 `PYTHONHASHSEED` 算出不同 DPS（随机 18/300 = 6 % 不一致，
偏差可达数百）。根因是 `set` 直接迭代（`rotation.py:838`、`parse_damage` 的 `types` 等）。
不修则不能安全并行、结果不可复现。修法：`set(...)` → `sorted(...)` + 多种子一致性回归。

**GPU（RTX 5090）明确否决**：热路径是字符串/路径/正则处理，修完层 1 后算术量极小；
上 GPU 只能重写整个伤害模型为张量式（大重写 + 偏离已验证口径的高风险），
且环境无 torch/cupy/numba。投入产出远不如缓存三连。

## 第九轮：性能优化「阶段 2」—— 并行独立搜索链（`gd auto --chains N`）

### 交付

```bash
python -m gd auto Sam --chains 4                      # 4 条链并行，取最优
python -m gd auto Sam --extreme                       # 极限模式自动 min(核数,8) 条
python -m gd auto Sam --chains 4 --anneal-iters 4000   # ★ 完全可复现
```

实现在 `tools/autobuild.py`：`run_chain()`（单链：扰动→贪心→退火）+ `_chain_init/_chain_run`
（spawn worker，每进程加载一次 gd.opt）+ `_run_chains()`（进程池，取最优）。

### ★ 实测（Sam lv69，同样 30 s 退火预算）

| | 墙钟 | 结果 |
|---|---|---|
| `--chains 1 --anneal-seconds 30` | 33.5 s | 94,126（37,173 次试探，**0 次改善**） |
| `--chains 4 --anneal-seconds 30` | **35.6 s** | **95,369（+1.3%）** |

同样时间预算、4 条链找到更好的解 —— 这就是「并行独立链」相对「把一次搜索拆开并行」的价值
（后者受 Amdahl 限制，只能省评估那 18~69%）。

### 关键设计

- chain 0 用 `perturb=0` **完整复刻单链** ⇒ 并行结果**必定不劣于**单链；另有起点兜底。
- 其他链随机扰动 1~3 个「仍满抗」的槽 + 不同退火种子 → 落到不同盆地。

| B-% | `offensive*ResistanceReductionPercent` | 物品 60+ / 星座 / 物品技能 | `-X% 目标抗性降低` | **取最强** |
| B-abs | `offensive*ResistanceReductionAbsolute` | 物品 63 / 技能 | `-X 目标抗性`（无 %） | 叠加 |

判定依据：`data` 里 16563 条本地化文本中 `DamageTotalResistanceReductionPercent` = 「% 目标抗性降低」、
`DamageTotalResistanceReductionAbsolute` = 「目标抗性降低」（无 %）、`DefensePierce` = 「{%.0f0}% 穿刺抗性」。

参照构建实测：刺骨战吼 lv12 −30%、夜之寒气 lv7 −19%、暗杀者的标记 −8% → **−57% 穿刺抗性**。
对 33% 抗性敌人 = **1.85×**，对 80% 抗性 Boss = **3.85×**。
⇒ **减抗是 GD 最大伤害乘区，而我们的模型完全没有它**，优化器会系统性低估减抗件。

### ★ 阶段 2 的实测偏差（计划被数据推翻）

### ★ 修掉的真 bug：`O.key()` KeyError 'conv_net'
`FLOOR` 加了 `conv_net`（= −1e9，转化可为负），但 `W_PEN` 没加 ——
而惩罚项是 `for k in FLOOR: W_PEN[k] * max(0, FLOOR[k] - o[k])`，
退火/束搜索的排序路径**直接 KeyError**。
是新写的 `selftest [16]` 断言「三表必须覆盖全部 FKEYS」抓到的（自检的价值现场证明）。
修法：`W_PEN['conv_net'] = 0.0`（权重 0 合理：FLOOR 已是「不设下限」）。
教训：**新增代理维度时，`FLOOR` / `W_DMG` / `W_PEN` 三张表必须同步**。
