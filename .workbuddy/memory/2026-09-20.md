### ★ Q6：`crit` 口径撕裂的修法

写死 `W_DMG['crit']=1.00` + 模型对暴击零响应 ⇒ 优化器把「+40% 暴击伤害」按线性 % 伤害估价。
现在由真实口径推导：

```
W_crit = W_total × [(暴击率/100)/期望倍率] ÷ [1/(100+pct_ref)]
pct_ref = 调和等效：1 / (Σ_t share_t/(100+pct_t)) − 100
```

★ 必须用**调和**而非算术均值（`1/(100+pct)` 是凸函数，算术口径实测偏 1.7%）。
Sam 实测每点实战 DPS：全伤害 38.5 / 暴伤 **15.7** / 穿刺 26.8 / 流血 8.1
⇒ `W_crit = 0.53`（写死值高估 **1.88 倍**）。解析 vs 有限差分差 **0.20%**（selftest [21] 断言）。
边际入口：`tools/plan_dps.py::marginals(char)`。

## 护甲/破甲收口（用户指令：「怪物元素护甲值不管，只需要知道输出循环的主要输出属性中

### 先把机制查清（结论全部有据，不是猜）

- **官方口径：护甲只吃物理直伤。** 两条护甲公式的输入变量逐字是 `physicalDamageDV`
  （`data/combatformulas.json` → `physicsDamageDefenseEquationDLEP/DGP`）。
  ⇒ **「元素护甲」在本作里不存在**：元素的减伤通道是**抗性**（`gd/rr.py` 的 10 个桶）。
  所以「怪物元素护甲值」既拿不到（离线库无 `defensiveProtection`）也**不需要**。
- **玩家的「破甲」不是「降低目标护甲」，而是护甲穿透**：`offensivePierceRatio`
  （武器「%护甲穿透」）把**残余物理转成穿刺**，穿刺**绕过护甲** ——
  已在 `gd/dmg.py::_apply_pierce`，是转化链**最后一步**。全库 **209 件**物品带它。
- **`DamageDurationDefensiveReduction`（「点目标护甲降低」）才是字面意义的破甲**，
  但 **玩家侧没有**：实测普查 `itemdb.js` 0 次、`skills_json.js` 0 次、
  `monsterdb.js` **80 次** ⇒ 只有怪物能破玩家的甲。
  ⇒ 结论：破甲做**挂点**（参数 `armor_reduce` / `--enemy-armor-reduce`），不做假维度。
- ★ **新挖到的官方常数：怪物护甲吸收率 = 56%**。
  推导链（两条官方常数相乘）：`engine.armorDefensiveAbsorption = 70`
  × `(1 + monsterAdjustments.defensiveAbsorptionModifier(−20)/100)` = **56**。
  ★★ 关键细节：吸收修正是**乘法缩放**（`calc.js::f62k` 逐字
  `min(engine.armorDefensiveAbsorption*(1+absorbModifier/100), 100)`），
  **不是**加减百分点（`70−20=50` 是错的）。三难度 × 四玩家数共 12 格全是 −20。
  代码里这个值**带依据串返回**（`monster_absorption()` → `(56.0, '推导：70% × (1 + (-20)/100)')`），
  不当成「真值」用。

## 阶段 9：雪崩流性能诊断 ——「优化没用上」的真相

（用户口径：「怎么跑这么久 昨天不是优化了算法吗？而且 cpu 占用极少 优化也没用上」）

### 现象

上一条 `autobuild.py Sam --archetype avalanche --with-weapon --jobs 8` 跑了 4 分半
未出结果（实际预计 **15 分钟**），整机 CPU 占用极低。

### 铁证（psutil 采样）

| 项 | 值 |
|---|---|
| 机器 | 16 物理核 / 32 逻辑核 / 63.7 GB（可用 39.5 GB） |
| autobuild 进程 CPU | **99.9%（吃满 1 核）** |
| 整机 CPU | **6.1%** |
| 日志首行 | 「并行链 **1**」 |

### 根因（四层，缺一不可）

1. **`--jobs` 是误导性参数**：只作用于满抗束搜索重启的 `ThreadPoolExecutor`，
   被 GIL 锁成近似串行（作者在 `run_cap_search` 的 docstring 里早写明
   「74 s ÷ 6 = 12 s/次，正是单次耗时」）。**且默认值 = 物理核 16** ⇒
   传不传、传多少，对总墙钟几乎无影响 —— 这是最误导的地方。
2. **真并行 = `--chains N`**（`mp.get_context("spawn")` + `Pool(n)`，每链独立单线程）。
   普通模式默认 `chains=1`，`--quick` 也是 1；只有 `--extreme` 才自动铺 `_logical_cores()`。
   我传了 `--jobs 8` 没传 `--chains` ⇒ 单进程单线程。
3. **局部搜索才是瓶颈**：日志时间账 —— ILP 只用 **5.0 s**（昨天换算法的优化**确实有效**），
   剩下 **279 s 花在 9 个槽** 上 ≈ **31 s/槽**（`--topk 60` 串行实算）× 14 槽 × 2 轮
   ≈ **15 分钟单链**。所以「快」要靠 `--quick` / 调小 `--topk`；`--chains` 是**买搜索量**
   （墙钟 ≈ 单链），不是变快。
4. **伴生坑**：`… | tail -60` 把输出缓冲到进程结束才吐 ⇒ 全程零进度，误判「卡死了」。

### 修复（已落地）

- `tools/autobuild.py`：
  - 显式 `--jobs N`（N>1）**自动转成 N 条并行链**，兑现用户的并行意图；
  - ★ 该判定必须排在 `--quick`/`--extreme` 预设**之前** —— 第一版放在后面，
    被 quick 分支先置成 1 条链（**当场又踩一次**，日志仍打「并行链 1」）；
  - 单链运行时主动打印「本机 N 逻辑核，搜索只占用 1 核」提示；

## 第二轮：搜索器换代（LNS 替代退火）+ 报告「伤害循环」章节

用户口径两条：
1. 「**放弃退火这个方案 太慢了** 有没有更优秀的算法 可以去 GitHub 找一下思路」
2. 「**伤害循环这个条目要写在最终报告里** 一般是普通攻击 叠加很多普攻触发的效果
   如猛袭就会触发雪崩 和一些装备上的技能哪些 调研一下」

### ① 退火的病灶（实测归因）

`tune_dps.anneal_search` 两个结构性缺陷：
- 温度挂**墙钟**（`frac = el / budget_s`）⇒ 420 s 预算下降温极慢，大半时间在高温随机游走
- `moves` 随预算变大（`>=180 s` 加四槽联动），随机挑 4 槽几乎不可能同时满抗
  ⇒ 绝大多数迭代 `okp=False` **直接 continue，连评估都没做**

实测：退火 100 轮只做了 **65 次真实评估**；从 94,474 再退火 47 s 到 117,457，
而 30 条链各跑满 420 s 只到 94,474 ⇒ **预算成了负资产**。

### ② GitHub 调研落点 = LNS（大邻域搜索）

- Pisinger & Ropke 2010《Large Neighborhood Search》
- `N-Wouda/ALNS`（Python 实现，含 ILS/VNS/GRASP 作特例）
- **OR-Tools CP-SAT 官方 Primer 明说「LNS 往往优于其他所有方法」**（destroy & repair）

### ③ 新实现 `tune_dps.lns_search`

每轮 = 一次 destroy & repair：
- destroy：随机挑 k 个槽（ks=(2,3,4)）放开，其余槽**硬固定**
- repair：邻域内**向量化精确枚举**（numpy 广播算「抗性和 + 代理和」，
  再按剩余抗性需求掩码剪枝），只对代理 top-`eval_cap` 算真实 DPS
  （真实评估 2.4 ms 是瓶颈，代理**只用于排序**）
- accept：**LAHC**（Late Acceptance Hill Climbing，历史队列），**无温度无降温**

实测（起点 `Sam_best_raven2.json` = 94,474，同种子）：

### 实测：并发 vs「串行 + 大池」（6 形态 × 400 轮 LNS，同口径）

| 布局 | 每实例 procs | 总进程 | 总墙钟 | 相对串行 |
|---|---|---|---|---|
| 串行（原地做法） | 16 | 16 | 244.6 s | 1.00× |

| 并发 budget=18 | 3 | 18 | 108.1 s | 2.26× |
| **并发 budget=24** | **4** | **24** | **90.0 s** | **2.72×** ← 拐点 |

⇒ 总进程数**可以超过**单池最优 16，因为重叠的是独立进程的串行段。

### 联网调研：敌方抗性减到负数会不会锁 0（用户提问）

- ★ **结论：不锁 0。** 敌方抗性可减成负，负值 **1:1 放大伤害**：
  `倍率 = (100 − r) / (100 − 基础抗性)`。实测口径见 `docs/rr_mechanics.md`。
- **三族减抗（措辞即判据）**，顺序 **B → C → A**：
  B `−n% 类型抗性`（技能行无持续时间）⇒ **叠加**；C `n% Reduced target's Resistance` ⇒ **取最高**；
  A `n Reduced target's Resistance`（无 %）⇒ **取最高**。A/B 可成负。
- ★ **推翻旧 wiki 说法**：C 类「不能低于 0」是错的 —— 官方论坛《Advanced Mechanics》给出
  负抗性修正 `r × (1 + n%)`（把负值推得更深），例 `−54% × 1.30 = −70.2%`。
  ⚠ 2019 年另有帖子说 C 类对负值无收益（拉回 0），两派并存；本库按 **+n%** 实现。
- ★ **−100% 下限无官方证据**：社区实例出现 **−118% ⇒ 2.18×**；「−100%」只是第三方
  计算器 calculator.city 的自设假设。本库钳 −100% ⇒ **保守、会低估**极端减抗流。
- **本库对拍（`gd/rr.py`）**：Sam 实测 `python -m gd rr Sam` ⇒ 技能/星座
  物理 −4% / 穿刺 −38% / 冰冷 −25% / 流血 −40% / 混乱 −25%，**装备词缀 0**，
  **C 族（max）为空** ⇒ **减抗全来自 B 类，模型完全正确，现有报告数值不受影响**。
- **三处潜伏偏差（待批准再改）**：① A 类 `…ReductionAbsolute` 当前混进 `add` **求和**，
  应为**取最高**；② C 类 `…ReductionPercent` 无条件 `× max(0,1−pct/100)`，对负值应改 `× (1+n%)`；
  ③ 顺序应为 B→C→A 而非 (B+A)→C。触发条件 = build 带**装备侧** A/C 类减抗
  （全库 `itemdb.js` A 族 189 处 / C 族 90 处；`skills_json.js` 两族皆 0）。
- **产物**：新增 `docs/rr_mechanics.md`（调研 + 对拍 + 修复方案 + 来源链接）。

## 4. ★★★ 找到并修掉真 bug：`--fit-buffer` 对「本来就过阈值的属性」完全失效

`gd/reqfit.py::solve()`：
```python
for k in ('physique', 'spirit'):
    if pmin[k]:                       # ✗ 只在「必须投点」时才加余量
        pmin[k] += max(0, int(buffer))
```
`pmin[k]` = **达到阈值所需的最低点数**。面板本来就过阈值时 `pmin[k] == 0`
⇒ **buffer 一点不加** —— 而这正是最常见的情形。

实测（`solve('Sam', buffer=N)`）：

|---|---|---|---|
| 0 | 0 | 438 | +9 |
| **1 / 3 / 10 / 40** | **全是 0** | **全是 438** | **全是 +9** |

⇒ **`--fit-buffer` 调到 40 都不动体格**。而同一次调用里 `pmin['spirit']=11 > 0`
却能拿到 buffer ⇒ **两个属性待遇不一致**（这就是「动态调整属性没生效」的技术真相）。

**修法**：判据改成「该属性**有需求**就留余量」：
```python
for k in ('physique', 'spirit'):
    if need.get(k):
        pmin[k] = pmin.get(k, 0) + max(0, int(buffer))
```

**修后实测**（同一个方案）：

| buffer | 体格点 | 面板体格 | 余量 | 狡诈面板 |
|---|---|---|---|---|
| 0 | 0 | 438 | +9 | 1127 |
| **1（默认）** | **1** | **446** | **+17** | 1111 |
| **3（推荐）** | **3** | **462** | **+33** | 1077 |
| 10 | 10 | 518 | +89 | 961 |

⇒ **默认 buffer=1 现在能给出 17 点余量**，覆盖 §3 夹逼出的 9~21 点偏差区间下沿；
**要稳妥建议 `--fit-buffer 3`（余量 33）**。

# 阶段 20 · 「抗性为什么溢出 255 点」—— 来源分解（新增 `tools/res_audit.py`）

3. **字段粒度决定下限**：三合一 ⇒ 上排最小可行值被"最弱项"绑定。

⇒ 结论：**溢出确实是纯浪费（游戏里 80% 硬上限，不转化），但边际成本为零** —— 换掉它只会掉伤害。

## 3. ★★★ `tune_skills` / `eval_build_variants` 漏传 `rr=`（陷阱 #58）

它们调 `final_report()` 时**没传减抗包**，而装备搜索（`dps_of`）**带了** ⇒ 差 **47%**：
同一套主穿刺装备，穿刺桶 **112,233（带 RR）vs 76,090（不带 RR）**。
后果不是「数字不准」而是**技能/星座是在错误的目标上挑的**。
已统一成 `RRKW = dict(rr=…, enemy=…, enemy_armor=…, enemy_armor_src=…)`，
所有 `final_report()` 调用 `**RRKW`（⚠ 别再显式传 `enemy=`，会重复关键字）。

## 4. ★★ `--goal fullres` = 「只求满抗、不优化伤害」（陷阱 #59）

第一次跑主穿刺搜索误传 `--goal fullres` ⇒ 日志一路正常、还打印「覆盖 1070/1070」，

判据：`评估次数` 个位数 ⇒ 目标选错了。
