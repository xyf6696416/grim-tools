## 一、先纠正一个问法

「用 CUDA 加速并行计算」这句话在**当前架构**下会对不上焦。现有实现**已经是并行**的了：

```
gd auto --extreme            → 4 条独立链（进程）× 每链 4 个评估进程 = 16 进程 = 物理核
                             每条链内部：LNS 逐轮串行（destroy&repair → 批量评估）
```

也就是说 **并行度已经吃满 16 核**，瓶颈不是「没有并行」，而是
**每个并行单元内部是纯串行标量 Python**。

⇒ 真正该问的是：**有没有一种算法/数据布局，能把「评估 N 个候选」从 N 次串行 Python
变成 1 次张量批算？** 那才是 GPU 能咬住的东西。

## 二、实测瓶颈画像（决定一切）

### 2.1 单次真实评估 ~1.45 ms（本次测）/ 3.04 ms（`_xyf` 大角色）

| 组成 | 占单次 | 性质 |
|---|---|---|
| `load_char` | ~19%（0.62 ms） | **读档 + 二进制解析 + dict 合并** → 纯串行 |

| **真实评估**（逐候选标量 Python） | **98%** | ❌ 见 §3 |

| 块 | 耗时 | 备注 |

## 三、CUDA 的诚实结论：**不改数据布局 ≈ +2%**

| 环节 | GPU 能不能帮 | 为什么 |
|---|---|---|
| 邻域构造 | 理论可以 | 占 **2%**；数据量小（~1e3 行 × 11 维），H2D/D2H + kernel 启动（~10 µs 起）> 计算本身 |
| 真实评估 | **不能** | 逐候选做 dict 查找、技能记录名字符串处理、条件分支（转伤/触发/WPS 判定）。**分支发散**是 GPU 的死穴；且每候选只有几千 FLOP ⇒ 算术强度极低 |
| 代理评分（线性加权和） | 可以 | 但它**本来就是**最便宜的一环（纯 numpy 向量），GPU 搬过去省不到可测量的量 |
| HiGHS ILP | 有 GPU 版（cuOpt） | 模型太小（2 万变量）⇒ 收益远低于迁移成本 |

**要 GPU 真正有意义，前提是先把伤害模型重写成「(N 候选 × M 技能) 张量批算」**
（见 §4 方案 B）——那是数量级工程，且下面 §5 的硬约束会直接挡住。

## 四、算法候选清单（**不一定 LNS**）

按「收益 / 风险 / 是否破坏逐位可复现」排序：

| # | 方向 | 做法 | 预期收益 | 破坏逐位可复现? | 工程量 |
|---|---|---|---|---|---|
| **A** | **代理模型驱动搜索**（surrogate / BO / 进化） | 用**已有的线性代理**（`W_DMG` 加权和，微秒级）在**大空间**上搜，只在最后对 top-K 做真实评估。把真实评估次数从 ~1e5 压到 ~1e3 | **最大**（评估次数 ↓10× 量级） | ❌ 不破坏（真实评估那一层没变） | 中 |
| **B** | **伤害模型张量化**（→ 可上 GPU） | 把 `load_char` + `final_report` 重写成对「候选批」的向量运算（torch/CuPy） | 若成功，理论上 10~50× | ✅ **破坏**（浮点求和顺序变 ⇒ 面板不可能逐位一致） | **极大** |
| **C** | **整体 MILP / CP-SAT 建模** | 装备选择直接做 MILP（满抗已经这么做）。难点：伤害含乘法与条件（转伤、触发、WPS 概率）⇒ 需分段线性化 | 中~大（能出**全局最优**） | ❌ 不破坏（但「最优」的定义仍是模型口径） | 大 |
| **D** | **槽位分解 + DP/剪枝** | 若目标可分离则 DP；但全局 % 加成、抗性需求是**交叉项** ⇒ 不能简单分解 | 小 | ❌ | 中 |
| **E** | **换搜索内核**（束搜索/GA/CMA-ES/MCTS） | LNS+LAHC 只是其中一种。可 A/B 对比 | 未知（要先有基准） | ❌ 不破坏 | 小~中 |
| **F** | **热路径工程化**（去 IPC / 缓存 / numba） | ① `load_char` 对同槽候选共享 base 解析 ② 把 16 进程 × 150 MB 的重复解析改成线程池 + 共享只读数据 ③ 关键循环 numba/Cython | 中（单次 1.45 ms 里有 19% 是 load_char） | ❌ 不破坏（可逐位对拍） | 小~中 |

## 六、建议的调研顺序（先便宜、先不破坏契约）

1. **先做基准台架**（半天）：固定一个角色+形态，跑 N 次同参数，记录
   「真实评估次数 / 墙钟 / 最优 DPS」，作为后续一切对比的**唯一基准**。
   现在有 `GD_LNS_SPLIT`、`LNS 单轮耗时`、`proc_tree.py` 三个观测点可复用。
2. **试 A（代理驱动）** —— 不动伤害模型 ⇒ 可逐位验收，收益上限最高。
   先做**离线实验**：把手上的 4 份 sweep 日志里的 (候选, 真实DPS) 抽出来，
   量「代理与真实 DPS 的秩相关」有多高。**秩相关够高 ⇒ A 必然有效**。
3. **试 F（热路径）** —— 纯工程，可逐位对拍，风险最低。
4. **再评估 C**（整体 MILP）：先做**可行性证明**（小规模：3 槽 + 分段线性化），
   能解出与 LNS 相同或更好的解才继续。
5. **最后才考虑 B（张量化 / CUDA）** —— 并且要你明确接受「重建锚点」。

## 七、给「CUDA 验证」的最小可行实验（如果你想先看到 GPU 到底怎样）

不动生产代码，单独写一个对照实验：

| 步骤 | 内容 |
|---|---|
| 1 | 把**评估张量化**做成一个独立原型：输入「N 个候选装备组合」→ 输出「N 个 DPS」，全用 torch.cuda |
| 2 | 只实现**能被线性化**的那部分（平伤/加成/抗性），把条件分支（转伤/WPS/触发）**先固定成常量** |
| 3 | 与 CPU 版对拍：**先比速度**（N=1e3/1e4/1e5 的吞吐），**再比数值差**（这里必然有差 ⇒ 用来量化「破坏逐位一致」的代价） |
| 4 | 若吞吐优势 ≥ 10× 且数值差可接受 ⇒ 再谈怎么把条件分支也张量化；否则结论就是「这条路不通」 |

★ 这个实验**只在 `scratch/` 下写原型**，碰不到生产链路，也就能随时丢。

## 九、结论与待你拍板

### 一句话结论
**别碰 GPU，先把搜索策略换成「代理驱动 + 热路径工程」。** 现有架构并行度已吃满 16 核，
瓶颈在「每个并行单元内部是纯串行标量 Python」——这部分 GPU 咬不住（98% 占比、分支发散），
仅在 2% 的邻域构造上 GPU 才理论有效但收益被 kernel 启动开销吃光。CUDA 在**不改伤害模型数据布局**的前提下 ≈ **+2%**，没意义。

### 推荐路线（按风险从低到高，全部可逐位验收）
| 优先级 | 方向 | 为什么先做 | 验收方式 |
|---|---|---|---|
| **P0** | **A 代理驱动搜索**（surrogate / BO / 进化） | 收益上限最高（真实评估 ~1e5→~1e3，≈10×），**不破坏逐位可复现**（真实评估那层没变） | 先把现有 sweep 日志里的 (候选, 真实DPS) 抽出来，量代理与真实的**秩相关**；够高 ⇒ 直接有效 |
| **P1** | **F 热路径工程**（共享只读解析 / 线程池 / numba） | 纯工程、零契约风险、`load_char` 19% 可压 | 同进程 A/B，面板逐位一致 |
| **P2** | **C 整体 MILP / CP-SAT** | 能出**全局最优**，但伤害含乘法/条件需分段线性化 | 先 3 槽可行性证明，解出 ≥ LNS 才继续 |
| P3 | B 张量化 / CUDA | 唯一能上 GPU 的路，但**必然破坏逐位可复现** | 需你明确接受「重建全部锚点」才启动 |

### 需要你决定的三件事
1. **是否批准先做 P0（代理驱动）的离线秩相关实验？** —— 不动任何生产代码，只在 `scratch/` 下把现有日志的 (候选, DPS) 拉出来算秩相关，半天出结论。
2. **普查那 3 个作废组合（爆破者/萨满/士兵）现在重跑吗？** —— WPS 判据已修（复用 `gd.alloc.is_wps`），重跑命令已就绪；建议用 `--batch 3 --budget 9 --low-priority` 错峰，别再爆内存。
3. **是否接受「方案 B 重建锚点」这个长期选项？** —— 现在不用做，但先给个口径，免得以后讨论起来反复拉扯。
