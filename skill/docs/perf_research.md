# 性能优化调研报告（2026-09-19）

> 结论先行：**真正的瓶颈在「纯 Python 伤害模型里的重复计算」，不在算力。**
> 两处缓存就能让单次评估快 **3.3~10×**（结果逐位不变）；
> 多进程（32 核）实测只值 **2.0~3.5×**，且受 Amdahl 限制；
> **GPU（RTX 5090）不适合这个负载**，不建议。
> 另发现一个**必须先修的不确定性 bug**：伤害模型受 `PYTHONHASHSEED` 影响。

## 二、瓶颈定位（三层，均已实测）

### 层 1 ★★ `skill_children()` —— 每次评估都把整个技能库重算一遍

`gd/rotation.py:807` → `children_pre = skill_children(skills)`，
其中 `skills = _load('skills.json')`（**静态全库，12 372 条**）。

`skill_children` 遍历全库、对每条做 `os.path.basename` / `os.path.dirname` / `re.sub`：

```
cProfile（200 次 final_report）:
  rotation.py:365 skill_children  tottime 1.174 s  cumtime 4.984 s   ← 占 final_report 的 89 %
    re.Pattern.sub              667 800 次
    ntpath.basename             680 800 次
    ntpath.dirname              667 800 次
```

即 **每算一次伤害 = 3 339 次正则替换 + 3 339 次路径字符串处理**，而结果**只依赖静态技能库**。

**修法（~5 行）**：按 `id(skills)` 记忆化。`_load` 返回同一对象，缓存天然命中。

**实测**：单次评估 **0.0255 s → 0.0078 s（3.3×）**，DPS **逐位不变（95 433）**。

### 层 2 ★ 存档重复解析

`gd/dps.py:143` → `d = S.parse(p)`，每次评估都重新解析 28 KB 的 `player.gdc`。

**修法**：按 `(path, mtime, size)` 缓存解析结果（只读用途）。

**实测（叠加层 1）**：单次评估 **0.0225 s → 0.0025 s（10.4×）**，DPS **逐位不变（95 433）**。

### 层 3 串行开销 —— 优化评估之后它变成主要矛盾

`anneal=0` 的 greedy+pair 段：33.6 s 里只有 13.2 s 是评估，**20.4 s 是串行**：

| 串行项 | 实测 |
|---|---|
| `import gd.opt`（模块级会跑一轮启动搜索） | **6.9 s** |
| 候选池构建（14 槽，5 491 条，`prune_cands` 首次） | **6.0 s** |
| 其余（`feas()` 扫描、记账、报告） | ~7.5 s |

> 评估优化后同一段：评估 4.0 s、挂钟 24.8 s（**评估占比 39.2 % → 16.1 %**）——
> 瓶颈已明显转移到串行部分。

## 三、方案对比（都基于实测，非估算）

| # | 方案 | 实测收益 | 工作量 | 风险 | 评价 |
|---|---|---|---|---|---|
| **A** | **缓存 `skill_children`**（记忆化静态父子表） | 单次评估 **3.3×**，结果不变 | **~5 行** | 极低 | ★★★ 首选，性价比碾压 |
| **B** | **缓存 `S.parse`**（存档只读解析） | 叠加 A 后 **10.4×**，结果不变 | ~15 行 | 低（只读用途；写盘路径不受影响） | ★★★ 首选 |
| **C** | **多进程并行**（`Pool`，32 核） | 评估吞吐 **P=4 → 2.0×｜P=8 → 2.9×｜P=16 → 3.5×** | 中（~150 行 + 重构 import 副作用） | **中高**：spawn 下每 worker 重跑 6.9 s 启动搜索；**且当前结果跨进程不一致（见 §四）** | ★★ 次选，必须等 §四 修完 |
| **D** | **并行多条独立搜索链**（每进程跑完整一轮，取最优） | 近线性（N 进程 ≈ N 倍搜索量） | 小（复用 C 的骨架） | 低（进程间无共享状态） | ★★★ 绕开 Amdahl 的正解 |
| **E** | `prune_cands` 落盘缓存 | 省 ~6 s / 轮 | 小 | 低（按等级+名额+物品库签名卡失效） | ★★ 顺手做 |
| **F** | 拆掉 `gd.opt` 的模块级启动搜索 | 省 ~6.9 s / 进程 | 小（挪进 `if __name__`） | 低 | ★★★ 顺手做，也是 C/D 的前提 |
| **G** | numpy 向量化伤害模型 | 上限高，但**收益不确定** | **大**（重写 `final_report`） | **高**：模型是分支密集的标量逻辑（逐技能、转化、DoT、改造），向量化极易与已验证口径偏离 | ⚠ 不建议现在做 |
| **H** | **GPU（RTX 5090）** | **≈ 0** | 大 | 高 | ❌ 见 §五，明确否决 |

### 组合后的预期（基于实测外推）

| 路径 | 现在 | A+B | +E+F | +D |
|---|---|---|---|---|
| greedy+pair 段（工作限定） | 33.6 s | 24.8 s | **~11.5 s** | ~9 s |
| 极限模式（退火 420 s 预算） | ~520 s | 墙钟不变、**搜索量 ×5.3** | 同左 + 省 13 s | 同左，**再多条链** |

> ★ **注意一个反直觉点**：退火是**固定墙钟预算**（`--anneal-seconds`）。
> 评估变快**不会缩短墙钟**，而是同样的时间跑 5.3 倍提案 ——
> 收益体现为**结果更好**，不是"跑得更快"。想要更快，得显式调小 `--anneal-seconds`。
> 实测：`anneal=90` 时 4 993 次 → 26 712 次评估，墙钟 123.8 s → 116.7 s。

## 四、★ 必须先修的 bug：伤害模型跨进程不确定

**实测**：同一份方案，不同 `PYTHONHASHSEED` 会得到**不同 DPS**。

```
PYTHONHASHSEED=0      -> idx10=22232  idx14=29454  sum=948161
PYTHONHASHSEED=1      -> idx10=22232  idx14=29454  sum=948161
PYTHONHASHSEED=2      -> idx10=21814  idx14=28422  sum=946461   ← 不同！
PYTHONHASHSEED=12345  -> idx10=22232  idx14=29454  sum=948161
```

随机方案抽样：**18 / 300 条（6 %）结果不一致**，偏差可达数百（相对 ~1–5 %）——不是浮点舍入。

**根因**：模型里有若干处**对 `set` 直接迭代**，迭代顺序依赖字符串哈希：
- `gd/rotation.py:838` `for t in set(list(wflat) + list(wdot) + ...)` 建 `base100`
- `gd/rotation.py:105` `parse_damage` 返回的 `types` 是 `set`
- 另有 `by_deps` / `_seen` / `no_scale` 等 `set`

**为什么必须修**：
1. **多进程不安全** —— spawn 出来的每个 worker 哈希种子不同 ⇒ 同一方案在不同进程算出不同伤害，
   并行搜索会"各搜各的口径"，结果不可复现。
2. **单次运行结果不可复现** —— 换个进程重跑可能得到不同 BD。

**修法**：把这几处 `set(...)` 换成 `sorted(...)`（或 `dict.fromkeys(...)`），
然后加一条断言：**多种子下结果必须完全一致**。

## 五、GPU 结论：明确不建议

| 判据 | 实情 |
|---|---|
| 负载形态 | 搜索是**分支密集的标量 Python**（逐技能、伤害转化、DoT、装备改造），不是稠密矩阵运算 |
| 热路径性质 | 最大热点是**字符串/路径处理 + 正则**（`skill_children`）—— GPU 的绝对反面 |
| 修完层 1 后的余量 | 单次评估只剩 ~0.0025 s，含解析与建字典；真正的算术量极小 |
| 要做 GPU 只能 | 把上万个候选**批量化成张量**，即把整个伤害模型重写成向量式 —— 巨大重写 + 与已验证口径偏离的高风险 |
| 环境 | 无 torch / cupy / numba（需额外装 ~2.5 GB CUDA 包） |
| 投入产出 | 真要提速，**A/B/D 三项加起来**的收益远高于 GPU，且风险低得多 |

> 唯一说得通的 GPU 用途是**代理模型**（用已评测样本训一个回归器，在 GPU 上筛百万候选）。
> 但那引入近似误差，与「宁可不认，也不认错」的项目原则冲突 —— 列为**远期可选**，不进本轮。

# 阶段 2 实施结果（2026-09-19 19:4x，已完成）

## 交付：`gd auto --chains N`（并行**独立搜索链**）

```bash
python -m gd auto Sam                      # 默认 1 条链（普通跑：启动开销 > 收益）
python -m gd auto Sam --chains 4           # 4 条链并行（墙钟≈单链，总搜索量 ×4）
python -m gd auto Sam --extreme            # 极限模式自动 = min(核数,8) 条链
python -m gd auto Sam --chains 4 --anneal-iters 4000   # ★ 完全可复现
```

### 为什么不是「把一次搜索拆开并行」

拆开并行只能省**评估**那一段（占 18~69 %），串行的池构建 / 记账省不掉 —— 受 Amdahl 限制。
**并行独立链**是每条链各走完「贪心 + 退火」，进程间零共享，收益近线性。

### ★ 实测（Sam lv69，退火预算同为 30 s）

| | 墙钟 | 结果 DPS |
|---|---|---|
| `--chains 1 --anneal-seconds 30` | 33.5 s | 94,126（37 173 次试探，**0 次改善**） |
| `--chains 4 --anneal-seconds 30` | **35.6 s** | **95,369（+1.3 %）** |

**同样的时间预算，4 条链找到了更好的解** —— 这正是要的效果。
（chain 0 用 `perturb=0` 完整复刻单链 ⇒ 并行结果**必定不劣于**单链，另有起点兜底。）

### 可复现性：给退火加了「按迭代数停」

- `--anneal-seconds`（默认）按**墙钟**停 → 机器负载会改变迭代数 ⇒ **结果会抖**
  （实测两次 94,178 / 94,126）。
- `--anneal-iters N` 按**迭代数**停，温度表也按进度而非时间 ⇒ **完全可复现**。
  实测 `--chains 4 --anneal-iters 4000` 两次运行，**每条链 DPS 逐位一致**
  （94,126 / 92,078 / 94,126 / 94,126）。

### 启动开销

Windows 只能 `spawn`：每个 worker 要 import `gd.opt` + 加载离线库 + 建候选池。
阶段 1 把 `import gd.opt` 从 6.9 s 压到 0.45 s、`prune_cands` 从 6.1 s 压到 0.22 s（落盘缓存），
所以 4 条链的启动只多 **~1.6 s**。这是阶段 1 的红利 —— 没有阶段 1，阶段 2 根本不可用。

## 阶段 3（2026-09-19 23:0x）：满抗搜索换 ILP —— 原理与数字

完整报告在 `refs/status.md` §18，这里只留结论。

**为什么原来慢**：满抗搜索的 6 次重启用 `ThreadPoolExecutor`，注释写的理由是
「numpy 的数组运算会释放 GIL」——**这个前提对束搜索不成立**。束搜索主循环是
「Python 逐槽展开 + 大量**小数组** numpy 运算」，小数组的耗时大半在解释器和
per-call 开销上，几乎不释放 GIL。所以 74 s ÷ 6 = 12 s/次，正是**单次**耗时。

**为什么换 ILP 不只是快、还更准**：`_obj()` 在 `goal='worst'` + `GD_FULL=1` 下
`worst ≡ 1.0`、`cover ≡ 1070` 恒定，表达式退化成「技能分 − 紫装惩罚」——
**伤害项整个消失**。束搜索交出来的「满抗起点」在伤害维度上是随机的。
ILP 直接建模「9 条抗性硬约束下最大化伤害代理」，给出**全局最优**。

**并发在这里的真相**（★ 别再试了）：
- HiGHS 本机构建**只支持单线程**：`threads=4/16/32` 或 `parallel='on'`
  → 模型跑成 `Not Set`（0.00 s / `gap inf`），是**失败**不是变慢。
- 「拆问题并行」实测更慢：按 `Σleg = L` 拆 15 个子问题 × 16 进程 = **27.7 s**
  （单实例 9.0 s）。子问题加了等式约束后形状更难，L=0 一个就要 26.5 s。
- 真正吃多核的地方是 **N 条独立搜索链**（阶段 2 已做），不是拆 ILP。

**并行度改为逻辑核**：16 链（=物理核）时整机 CPU 均值仅 **39.5%**（峰值 60%）。
32 链后峰值 **98.6%**、均值 65.4%，**墙钟不变**（77 → 80 s），DPS +0.5%。
默认因此改成 `_logical_cores()`，上限由 `_cap_chains_by_mem`（每链 ~1.4 GB）兜底。

**数字**：满抗搜索 **74 s → 9.0 s（8.2×）**；全流程 100.9 s → **16.0 s**（同口径）。
自检 96 → **103 项**（新增 [15] ILP 满抗搜索）；复现 CPU：`tools/cpu_probe.py`。

# 阶段 11（2026-09-20 晚）：LNS 邻域并行 + 三处缓存 —— 以及「GPU 为什么不上」

> 本节同时回答用户两个问题：「LNS 不能继续优化吗？」「有没有可以让 GPU 参与计算的方案？」
> 完整口径见 `SKILL.md` §3.17 / §3.18。

## ① 单次评估：2.440 → 1.633 ms（1.49×）

| 缓存 | 位置 | 收益 | 安全前提 |
|---|---|---|---|
| `save_dir()` | `gd/paths.py` | 7.4% | 键含 `GD_SAVE`（override）；只缓存成功结果 |
| `Db.fields()` | `gd/dbr.py` | 19% | 每评估调 236 次；69 个调用点**无一修改返回值** ⇒ 可共享同一 dict |
| `fold(parts)` | `gd/dps.py` | ~10% | 纯函数；LNS 每轮只换 k 槽，其余槽**逐轮重复折叠**；返回浅拷贝 |

## ② 邻域并行 `tune_dps.ParEval`（主收益）

LNS 每轮的 `eval_cap` 个候选**互相独立** ⇒ 天然可并行。480 个候选实测：

| 进程数 | 每次评估 | 相对串行 |
|---|---|---|
| 串行 | 5.198 ms | 1.0× |
| 8 | 0.375 ms | 13.9× |
| **16** | **0.274 ms** | **19.0×** ← 最优（默认 `procs=16`） |
| 24 | 3.254 ms | 1.6× ← **超订劣化** |

★ **池要建一次、全程复用**（`ParEval.warm()`，约 2.2 s 固定开销）。把建池放进计时会得出
「并行没用」的**错误结论**（实测踩过：24 进程显示 0.7×）。
★ worker 用 `(char, arch)` 重建评估 —— `real_dps` 是闭包（含 memo），跨进程不可 pickle。
★ **并行路径必须先吃调用方 memo**（`make_real_dps` 挂在 `f.memo` 上）：否则 36,045 次
评估被重复成 60,478 次，**浪费 40% 墙钟**。
★ `--procs` 与 `--chains` **互斥**（叠加 = N×procs 进程必爆）。

端到端（600 轮，起点 94,474）：**串行 61.8 s → 并行 8.0 s**（LNS 本体 7.7×，含建池 6.0×），
结果**逐位一致** ✓。2026-09-20 收尾复测（120 轮，`probe31`）：17.9 s → 2.6 s（6.8×），
池内评估 10,335 次 / 2.3 s，一致 ✓。

## ③ ★ 负面结论：「加轮数」是无效方向

同起点同种子：**120 轮 == 600 轮 == 4000 轮 ⇒ 全部 122,337** ⇒ LNS 早已收敛。
4000 轮只是把墙钟从 61.8 s 拉到 234 s（串行）。
⇒ 真正的杠杆是**扩大邻域 k** 与**邻域构造**，不是轮数。

## ④ GPU 判据：这一轮**没有**上 GPU（四条硬理由）

1. **数据量差 3 个数量级**。单解 = 14 槽 × ~5 部件 = ~70 条记录，折叠后 ~2000 维、
   **~700 个非零**；GPU SpMV/SpMM 要 `nnz ≥ 10⁵` 才摊得开 kernel launch（~10 μs）
   与访存延迟 ⇒ 单解级别差 **~143 倍**。
2. **瓶颈根本不是数学运算**。优化后 profile：`final_report`（技能伤害的"算术"）
   `tottime` 只占 **11%**；其余是 `load_char` 的**字典/字符串/分支**
   （`dict.get` 4,384 次/评估、`setdefault` 4,524 次、`re.match` 895 次）。
   分支发散是 GPU 最差的场景。
3. **批量被满抗约束卡死**。实测满抗可行率仅 **0.4%**（k=3/topk=20：8000 组合只剩 31 个）
   ⇒ 每轮可评估候选只有几十~几百个，摊不开 GPU 固定开销。
4. **口径风险**。向量化伤害链路必然引入近似 ⇒ 触碰核心资产「面板逐位可复现」。
   而 CPU 16 进程已拿到 **19×（评估）/ 7.7×（LNS）**，成本是半天。

**GPU 唯一真正有价值的位置 = 邻域放大到 CPU 吃不住时（k ≥ 5）**：

| k | topk | 组合数 | 平均满抗可行 | P(可行 > eval_cap 240) |
|---|---|---|---|---|
| 3 | 18 | 5,832 | 206 | 29% |
| 4 | 18 | 104,976 | 2,472 | 62% |
| **5** | **18** | **1,889,568** | **30,225** | **87%** |
| 5 | 30 | 24,300,000 | 248,133 | 99% |

⇒ 默认参数（k ≤ 4）下代理只影响 29~62% 的轮次；一旦 k=5，每轮 3 万个可行解 =
eval_cap 的 **126 倍**，**「从 10⁶ 个组合里快速筛出真正好的 240 个」成为新瓶颈** ——
这正是 GPU（或更强的代理模型）该上的位置。届时路径：
`fold` 重构成「候选 × 属性」稀疏矩阵（可行：`needs_scale` 只依赖**单记录**字段 ⇒
每条记录贡献可独立预计算）→ GPU 批量 SpMM 折叠 + 打分 → 只对 top-N 用 CPU 精算。
⚠ 另需处理 `lns_search` 里 `total > 4_000_000: continue` 的**安全阀**
（k=5/topk=30 会被直接跳过）与内存（k=5/topk=18 的 `rac` 已 151 MB / topk=30 达 1.9 GB）。

# 阶段 12（2026-09-20 晚）：多形态并发普查 —— 比「串行 + 大池」快 2.7×

用户口径：「六个形态不能 6 个并发跑吗？」

## ① 先说结论

| 布局 | 每实例 procs | 总进程 | 6 形态 × 400 轮总墙钟 | 相对串行 |
|---|---|---|---|---|
| 串行（原地做法） | 16 | 16 | 244.6 s | 1.00× |
| 并发 `--budget 16` | 2 | 16 | 154.1 s | 1.59× |
| 并发 `--budget 18` | 3 | 18 | 108.1 s | 2.26× |
| **并发 `--budget 24`** | **4** | **24** | **90.0 s** | **2.72×** ← 拐点 |
| 并发 `--budget 30` | 5 | 30 | 98.1 s | 2.49×（已过拐点） |

★ **不是越多越好**：24 → 30 反而变慢。拐点在物理核 16 与逻辑核 32 之间的 **24**。
★ **结果逐位一致**：并发下 6 个形态的 DPS 与串行完全相同
（104,900 / 83,139 / 81,007 / 79,529 / 77,114 / 68,149）⇒ 并发只改墙钟。

## ② 为什么「串行 + 大池」浪费机器

单实例 LNS 端到端并行效率只有 **48%**（16 进程 7.7×）：`lns_search` 里有大量
**不可并行段** —— 邻域构造（笛卡尔积索引 + numpy 代理打分）、LAHC 记账、
`eval_cap` 截断、`_repair` 的 numpy 抗性修复。

串行跑 6 个形态时，这 6 份串行段**首尾相接**：整机 CPU 曲线呈「单核尖峰 → 多核平台」
交替，平台期以外白白浪费。并发布局下 6 份的**串行段与并行段互相填补**。
⇒ **总进程数可以超过单池最优值**，因为重叠的是「独立进程的串行段」，
不是同一个池在抢核（这与 §3.17「procs 超 16 就劣化」不矛盾 —— 那是**同一个池**）。

## ③ 内存不是约束（实测，`data/scratch/probe33_conc.py mem`）

`ParEval` 单 worker（含离线库加载）恒为 **143 MB**，procs=1/4/8/16 完全线性：

| procs | 1 | 4 | 8 | 16 |
|---|---|---|---|---|
| 树内合计 RSS | 294 MB | 723 MB | 1,294 MB | 2,437 MB |
| 均摊 / worker | 142.8 | 142.9 | 142.9 | 142.9 MB |

6×5 = 30 个 worker ⇒ ~3.6 GB。真正的约束是**核**（16 物理 / 32 逻辑）。

## ④ 真正的拦路虎：`autobuild` 的**全局单实例锁**

第一次真跑 6 并发时第 6 个形态被拒（`rc=4`）：
「✗ 已有一个 autobuild 在跑，拒绝启动第二个」。

锁的原始动因（同日早）：两个 autobuild 同时跑 ⇒ 一次 53 个 python.exe，
且**两个进程往同一个 `--out` JSON 写**。重看三条危害：
①（同文件覆盖）③（日志交错）**只在同一输出时发生**；②（进程数）是并发度预算问题。
⇒ 改为按 **(角色, 输出文件)** 取键（`_lock_key` / `_lock_path`）：
同输出仍互斥，**不同输出可并发**。
锁文件：`data/scratch/.autobuild.locks/<md5前12>.lock`，自带 PID，死进程自动回收。
`--force` 语义收窄为「抢占**同一个输出**」。
